# 当前来源请求的确认边界

## 触发与证据

2026-10-30，59版车机重启后首次连接，仪表自动全屏却显示原厂高德地图；保留进程后的一次暖重连显示CarPlay地图。车辆驻车、发动机运行，观察时ADB关闭，系统窗口快照在重新开启ADB后采集。

冷启动日志：23:11:33.601重建自身仪表窗口；23:11:35.963执行当前窗口来源请求；23:11:36.169/.174得到布局3及通道3；23:11:37.468才发出延迟全屏请求，23:11:44.994确认超时。重建的quiet窗口没有被显示监听放行，稍后快照仍为alpha=0。此晚采快照不能单独证明ADB关闭期间的物理来源复用器状态。

暖重连在第三次有限请求后取得完整确认，再显示窗口。这一次成功不能替代冷启动验收或长期可靠性验证。

## 修复

`InCallClusterBridge`原先在`beginConfirmation`设置不可达的回调序号，直到延迟的`requestLayout`才打开接纳边界；每次重试还会清空部分结果。来源序列本身返回的完整状态因此可能被丢弃，重复设置已生效的全屏又不保证产生新回调。

新增一个私有的`armConfirmation`：在当前视频窗口实际发出来源序列之前记录回调序号；没有来源请求的暖恢复仍在第一次实际布局请求前开启边界。同一代次只开启一次，后续重试保留本轮新收到的部分状态，反向状态仍会按原逻辑撤销对应标记。

完整新回调对经通用`onProjectionLayoutConfirmed`通知定制模块，允许当前来源请求在首次延迟重试之前结束恢复。普通布局通知仍走原`onProjectionLayoutRequested`，保留其对过早旧状态的防护；其他定制模块缺省沿用原布局通知行为。该区分避免“Host已经显示，但定制策略仍继续重试直到超时”的第二层时序问题。API注册器的兼容转发和异常隔离也有回归断言。

仍要求本轮新的布局3与通道3同时成立。已有缓存值、仅发送成功、只有一类回调均不能放行。当前窗口、手机会话与厂商代次隔离、退出和关闭自动全屏，以及每轮至多3次重试保持原约束。高德前台等待仍为2秒；本次没有增加等待或改变高德初始化入口。

改动落在已有协议桥接、通用确认通知与定制策略，不增加车辆协议入口、后台服务、用户设置或轮询。

## 回归

增加6项行为测试：来源请求的回调先于延迟布局重试、部分回调跨重试保留、缺一类回调仍超时、窗口结束后拒绝排队确认、反向状态撤销部分确认、Binder同步返回也可确认。

原`sourceDispatchAndOldFullValuesCannotConfirmCurrentWindow`把实际来源请求之后的新回调也标为旧值，与本次日志证明的有效早到回调冲突。修正其场景：将“旧值”注入放在实际来源请求之前；保留原全部断言和用例名，另外6项测试检查新的正负边界，不删除、跳过或放宽原保护条件。原59版失败日志和红灯测试结果在本地分析目录保留，不进公开树。

62候选以59版为基线，仅加入本项修复，便于实车归因；同一补丁同步到61版所在吸收支线，原先已签名的60/61 APK不被覆盖。离线测试、构建和签名校验不能替代新一轮冷启动画面来源的实车验证。
